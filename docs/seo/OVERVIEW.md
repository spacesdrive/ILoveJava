# SEO

## The CSR constraint

This is a client-side rendered SPA - no SSR, no server-generated HTML per route (see [../architecture](../architecture)). That means:

- `index.html` ships a static `<title>`/`<meta description>` fallback (crawlers that don't execute JS see this).
- The [`Seo`](../../src/components/seo/seo.tsx) component patches `document.head` on mount/route change for crawlers that do execute JS (this covers Googlebot; it does not cover every crawler).
- Anything that must be indexable independent of JS execution (long-term: individual lesson pages, if organic search matters for them) is a candidate for static prerendering at build time - evaluate `vite-plugin-ssg`-style prerendering before reaching for a server, per the backend rule in [../architecture](../architecture).

## Per-page checklist

Every routed page must set, via `<Seo />`:

- `title` - sentence case, no site name (the component appends `· ILoveJava`)
- `description` - one sentence, unique per page
- `canonical` - only when it differs from the current URL (e.g. paginated views canonicalizing to page 1)
- `image` - for pages worth sharing (triggers `summary_large_image` Twitter card)
- `noindex` - for error pages, drafts, or any page that shouldn't rank (see `NotFoundPage` for the pattern)

## Sitemap and robots.txt

Both are generated at build time, never hand-edited or committed as static files.

### Architecture

- [`src/lib/sitemap.ts`](../../src/lib/sitemap.ts) - framework-agnostic, unit-tested: `SitemapEntry`/`ChangeFreq` types, `validateSitemapEntries` (duplicates, invalid priority/changefreq/date, non-root-relative paths, query strings, hash fragments), `buildSitemapXml` (valid XML per the [Sitemap Protocol](https://www.sitemaps.org/protocol.html), with XML-escaping).
- [`src/lib/robots-txt.ts`](../../src/lib/robots-txt.ts) - framework-agnostic, unit-tested: `buildRobotsTxt`, allows all crawlers and appends the `Sitemap:` directive.
- [`src/app/sitemap-routes.ts`](../../src/app/sitemap-routes.ts) - the single source of truth for which static routes are indexable, as plain `SitemapEntry[]` data (no JSX/React import - it has to be importable from build tooling, see below).
- [`vite-sitemap-plugin.ts`](../../vite-sitemap-plugin.ts) (repo root, alongside `vite.config.ts`) - a Vite plugin (`apply: 'build'`, so it never runs under `pnpm dev`) that on `closeBundle` validates `staticSitemapRoutes`, throws (failing the build) if invalid, and writes `dist/sitemap.xml` and `dist/robots.txt` using [`SITE_URL`](../../src/constants/site.ts) as the single source of truth for the site's canonical origin - never a hardcoded domain.

### Generation process

1. `pnpm build` runs `vite build`, which loads `vite.config.ts` and registers `sitemapPlugin()`.
2. On `closeBundle` (after the app bundle is written), the plugin calls `validateSitemapEntries(staticSitemapRoutes)`.
3. Any validation error throws, which Vite surfaces as a build failure (`error during build: ...`) - an invalid sitemap cannot ship.
4. On success, `buildSitemapXml` and `buildRobotsTxt` write `dist/sitemap.xml` and `dist/robots.txt` directly into the build output directory. Neither file lives in `public/` or in source control - they're regenerated by every production build, so they can never drift from `SITE_URL` or the route manifest.

This is a single in-memory pass over a small, explicit list (no filesystem scanning, no crawling the built HTML) - cheap enough to run on every build regardless of how many entries exist.

### Route discovery

React Router's `createBrowserRouter` config (`src/app/router.tsx`) isn't file-based, so there's no filesystem to scan for "all routes" the way a Next.js `app/` directory would provide. Instead:

- **Static routes** (today: just `/`) are listed explicitly in `src/app/sitemap-routes.ts`. [`src/app/__tests__/sitemap-routes.test.ts`](../../src/app/__tests__/sitemap-routes.test.ts) asserts every path in that list resolves to a real route in `router.tsx` (via `matchRoutes`) and not the catch-all 404 - if a route is renamed or removed without updating the manifest, this test fails, which is the enforcement mechanism for "the sitemap can't silently drift from the router."
- **Content-driven routes** (lessons, exercises, quizzes, docs, blog posts, category/tool/landing pages once they exist) are not in this list and don't need to be added to it one by one - see [Future extension points](#future-extension-points) below.

### Excluded routes

Anything with no entry in `src/app/sitemap-routes.ts` is excluded by default (opt-in, not opt-out) - this covers the 404 page, and will cover any future error/test/sandbox/draft/admin/auth/private/experimental route without needing an explicit exclusion list. `NotFoundPage` additionally sets `<Seo noindex />` (see [`not-found-page.tsx`](../../src/pages/not-found-page.tsx)), which is the correct signal for a page a crawler might still reach by a broken link, independent of the sitemap.

### Maintenance rules

- Adding a new static, always-public page: add one entry to `src/app/sitemap-routes.ts`. Nothing else to touch.
- A route that shouldn't be indexed (draft, admin, auth, experimental): do not add it to `sitemap-routes.ts`, and set `<Seo noindex />` on its page component.
- Changing `SITE_URL` (e.g. a domain change): edit [`src/constants/site.ts`](../../src/constants/site.ts) only - both `sitemap.xml`'s `<loc>` values and `robots.txt`'s `Sitemap:` line derive from it.
- Custom crawl rules (a future `Disallow`): edit `CRAWL_RULES` in `src/lib/robots-txt.ts`, not a static `public/robots.txt` (there isn't one - it's generated).

### Future extension points

Once a content index exists (`src/content`, per [../content](../content)), add one function per content type that reads the index and returns `SitemapEntry[]` (e.g. `getLessonSitemapEntries()`, `getDocSitemapEntries()`), then merge its output into the `entries` array built in `vite-sitemap-plugin.ts` alongside `staticSitemapRoutes`. This keeps the pattern uniform: every content type contributes entries through the same `SitemapEntry` shape and the same `validateSitemapEntries`/`buildSitemapXml` pipeline, regardless of whether it's a static route or generated from thousands of content records. Do not build this ahead of a real content index - see the "no placeholder features" rule in [CLAUDE.md](../../CLAUDE.md).

### Structured data

Not yet implemented - added once there are real routes to describe. When lessons land: JSON-LD (`Course`/`LearningResource` schema) injected the same way as other head metadata (see [`Seo`](../../src/components/seo/seo.tsx)).

## URLs

Structured and stable: `/learn/<path-slug>/<lesson-slug>`, `/exercises/<slug>`, etc. Slugs are permanent (see [../content](../content)) - a URL that's been indexed should not need to change.
